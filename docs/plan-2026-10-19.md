## The diagnosis in one paragraph

The method (Section 3) and the laboratory evaluation (Section 5) are in reasonable shape. The weaknesses concentrate in
two places. (1) **Baselines are not chosen by one consistent rule.** Some experiments include a format-aware method
(the field-occlusion oracle in 5.1), others reject the same kind of method as unrealistic (the parser map in 6.2), and a
reviewer will call several remaining baselines weak (REVIEW W1, W3-W5). (2) **Section 6 is two independently developed
experiments**, not a coherent section. The audit (6.2) has a realistic attacker, held-out evasion, and a mitigation; the
comparison (6.1) has a threat model whose attacker never appears and measures only deletion. Their threat models
overlap and disagree, and 6.3 adds little. Both problems need the experiments pinned down first, so the order below is:
settle what each experiment claims, then the baseline rule, then rebuild Section 6, then the smaller items.

## Phase 1: pin down what each experiment claims (DRAFTED 2026-10-19: `docs/experiments/specs.md`)

The user's point: we are still settling what the experiments are, so a baseline debate now would be premature. Before
any new run, write one short spec per experiment (5.1, 5.2, 5.3, 6.1, 6.2), in the same format, in

- **Operator**: which transfer produces the result (pullback, pushforward, or P alone).
- **Measurement**: what is computed and compared, in plain terms.

- **Comparison class**: which competitors are in scope, and why (input to Phase 2).
- **Mock table**: the paper's table with placeholder numbers, the operator behind each column (per the "mock the

## Phase 2: one baseline rule for the whole paper (1 brainstorm session; after Phase 1)

Goal: a single, stated rule for which competitors each experiment faces, applied uniformly, so that no reviewer can
point to a method we include in one place and dismiss in another. Candidate rules to discuss:

- **(a) Format-agnostic comparison class.** Every baseline uses only what the transfers use: the model, its
  explainer, and the extractor (as code or as a black box). Format-aware methods (parsers, field maps) are a different
  class: they must be rebuilt per file format, which is what P avoids. Consistent with the user's 2026-10-12 decision
  that a hand-built parser map is not a realistic alternative, and with Phase 0, item 1. Cost: the paper must argue
  this class boundary explicitly (Sections 2 and 4), because the review shows a reviewer will raise the parser map
  regardless (REVIEW Q1-Q3).
- **(b) Strongest practitioner alternative, format-aware included.** Run the parser-based baselines everywhere
  (pullback coarsened to fields, IG summed per field, field-level triage). Strongest against reviewers; risks finding
  that on header fields the parser map matches us (REVIEW W1), which would force the claims toward "automation and
  coverage beyond fields".
- **(c) Tiered.** Format-agnostic baselines as the comparison, plus one format-aware *skyline* reported once (e.g., in
  5.1 or an appendix) to show what per-format engineering buys and costs.

For each rule, the session lists per experiment which baselines it implies, which already exist, and which need runs,
and checks every claim in the paper against it. Decision by the user. Inputs: REVIEW Sections 4-5 (missing baselines,
TRUSTEE, MAB-Malware, Aryal et al.), `PLAN.md` screening criteria.

## Phase 3: rebuild Section 6 to top-tier standard (largest block; ~4-5 weeks)

### 3a. One setting for both applications (writing)

A Section 6 opener states, once: the **defender** (owns a feature-based and a raw-byte detector and a labeled corpus,
instruments the extractor once); the **attacker capability** shared by both applications (changes the Windows loader
ignores or accepts, as in the audit; justified by prior functionality-preserving attacks: gym-malware, GAMMA,
Demetrio et al.); the **trust assumption** (the extractor's parse is trusted; parser differentials are out of scope);
and what is out of scope (appending, section injection, packing, execution). Each application then states only its
own goal and adversary goal. This removes the duplicated and inconsistent threat models (REVIEW 3.2).

### 3b. A common shape for both applications

Both follow the same four steps, so that they read as one design rather than two:

| step | 6.1 comparison (pullback, per file) | 6.2 audit (pushforward, corpus) |
|---|---|---|
| find | shared reliance; triage labels | candidate features from aggregated IG |
| confirm | deletion against size-matched controls (exists) | scrambling against same-window controls (exists) |
| realize | **new:** loader-safe changes to the found bytes | loader-safe evasion on fresh held-out malware (exists) |
| act | **new:** a defender action with a measured outcome | test-time mitigation (exists); retraining (blue) |

### 3c. The comparison (6.1): give it a realized outcome

The gap: no attacker acts and no outcome is measured (REVIEW W3). Candidate experiments, to be mocked and screened
first (Phase 1 spec), at most two chosen:

1. **Joint evasion through shared reliance.** Using the audit's loader-safe machinery, change the fields in the shared
   set S, and, as controls, as many fields from each detector's exclusive set and from neither. Hypothesis: changing
   S evades *both* detectors more often than the controls, because S is worth more to each model than its own
   exclusive bytes (the existing deletion result). This turns "shared reliance" from a deletion measurement into an
   attack outcome, in the same terms as 6.2. Mostly reuses existing code (`audit_*`). Risk: the shared set is mostly
   fields the GBDT reads as named features, which raises Phase 2's parser question again.
2. **Triage-routed action.** For files flagged by the GBDT alone, the "oppose" bytes hold MalConv's benign verdict.
   Measure whether re-scoring MalConv with those bytes neutralized confirms more true GBDT-only detections than false
   ones (a precision gain for the two-detector ensemble) (REVIEW risk 3b). Risk: a weak or confounded effect, since
   deletion itself pushes MalConv up (the fragility noted in 5.2); needs a careful control.
3. **Attack transfer** (the discussion's "load-bearing" TODO): whether published MalConv attacks transfer to the GBDT
   more often when they touch the bytes the GBDT's pullback marks. Most realistic and most expensive; only if 1 or 2
   fail.

Also: 100 files per triage cell instead of 25 (scale-up), and drop the attacker from 6.1's threat model if no option
above instantiates one (REVIEW 10.3 has a "setting" draft).

### 3d. The audit (6.2): close the review's open points

In priority order:
1. **Exercise the pushforward where it differs from summing per field.** Rerun discovery without the "run of at most
   256 bytes" filter and confirm features whose bytes are shared or scattered (imports, section names, strings) by
   scrambling the bytes P assigns, against matched random bytes (REVIEW risk 1b). This is the pushforward's real
   novelty claim (splitting shared bytes), currently unexercised. Needed under any Phase 2 rule.
2. **Replace the blue retraining row**: retrain MalConv with the audited fields zeroed (cluster/GPU; ~1 week).
3. **Mitigation against a stronger attacker**: one off-the-shelf functionality-preserving MalConv attack (e.g., DOS
   header or padding from secml-malware) on the unmodified and mitigated model, and frame the mitigation as targeting
   the audited reliance only (REVIEW risk 9). Note: the old "header-attack comparison" (M2) was dropped on 2026-10-14
   for complexity; this is narrower (one attack, evaluation only), but the user should confirm.
4. **0.1% FPR columns** from existing scores (hours).
5. **More than one MalConv** (seeds 1-2 of the EMBER-2024 checkpoints) so the reliance finding is not one model's

## Rule (a) and Section 6: the role split (2026-10-19)

Rule (a) restricts the *methods compared* (explainers, transfers, baselines) to format-agnostic ones. It does not
restrict the *evaluation harness*: the deletion operator, the struct trigger, and the loader-safe rulebook may use
format knowledge, because they are shared by every method and protect the experiment's integrity (CLAUDE.md, 2026-10-07).
So Phase 3's "realize" step does not break (a). Two real tensions remain:
1. A reviewer may argue that if acting on the audit needs a per-format rulebook anyway, a per-format parser map costs
   little more. Answer: a parser map consistent with the extractor's features is a hand-built partial P (for
   non-overlapping fields the pushforward reduces to it, Proposition 3(iv)); the two differ only where features share
   bytes, which Phase 3d item 1 (the unfiltered audit) tests. Rule (a) and that experiment support each other.
2. Keep the rulebook keyed on *feature names* (EMBER's field features), reached through P, not on a separate PE
   parser, so that format knowledge enters only through the threat model. This also tells 6.1's "realize" step how
   to change the shared bytes: map them through P to the features that read them, then apply the same rulebook.
