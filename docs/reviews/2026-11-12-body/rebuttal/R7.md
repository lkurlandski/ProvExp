# R7: The routed system is a bypass. Files outside the population go to an evadable detector; flagging them costs 1.5% FPR against a 1% budget; one field may move any file out (§5, item 1); the system is never evaluated end to end.

**Opinion:** change the methodology (already done in decision 11: no router, and the two entries the loader ignores added to the threat model; what remains is writing it into §4.4 and §5.4 and counting end to end at scale)

## The reviewers' perspective

All four reviewers raise it, and three of them (B, C, D) name it as the one change that would move their score. Only R1-R2 come close to that level of agreement.

The deployed system, as §4.4 describes it, has three parts. A check decides whether a file is in the *population*
(complete PE files with a plain layout, where the guarantee is proven). Files in the population go to the monotone
detector, and every other file goes to the unconstrained detector, which has no guarantee. The reviewers object that
a system is only as robust as its weakest path:

- **The bypass.** C-W1: "the robustness of the composite system is the robustness of the unconstrained branch, for
  any attacker who chooses to start outside the population". D-W2 calls the fallback "an unguarded bypass" and says
  that the paper "waves it off". It is robust only "for attackers who do not pick their starting point", and D would
  raise this first in a PC discussion. A-W4 (1) makes the same point: "Malware authors who control the build ... can
  ship out-of-population binaries from the start."
- **"Stand out" fails at the operating point.** A-W4, B-W3, C-W1 and D-W2 all check the same arithmetic: 1.5% of
  benign test files lie outside the population, which is more than the 1% false-positive budget. So flagging every
  file outside the population is not affordable, and "such files are rare among benign software, and so stand out"
  does not hold.
- **Leaving the population.** B-Q2 and D-Q1 ask whether an edit outside the threat model, such as "a data-directory
  entry pointing past EOF", takes a file out of the population. B-W3 (iv): "Closure under M does not exclude that."
  C-W1 asks for attempts to break closure on purpose.
- **No end-to-end number.** A-Q3, B-Q1, C-Q1 and D-Q1 ask for the evasion rate of the whole system, at a fixed
  false-positive rate for the system, against an attacker who knows about the routing. B-W3 estimates it at "10–13%"
  if about a quarter of malware lies outside, and at "around 5%" if 89% lies inside.
- **The 89%.** B-W3 and A-W4 (2) suspect the placeholder is optimistic (78.5% and 74% in earlier counts). D-W2 and
  D-Q7 ask for its denominator.

To change their scores, a reviewer would need three things. The first is a policy for files outside the population
that does not hand an attacker a weaker detector. The second is the system evaluated end to end at a fixed
false-positive rate, including an attacker who first moves the file out of the population or starts outside it. The
third is an answer to whether a write that keeps the file loadable can take a file out.

**Where they differ.** A and D treat the routing as a claim to be scoped (both weak accept). B and C treat it as a
security failure that decides the verdict (both weak reject, confidence 4). B adds that the population share should be
measured on complete files above 4 MB (B-W3, B-Q1). A and D want an alternative fallback evaluated (a monotone or
conservative detector; flagging at a stated cost). C wants the out-of-population policy specified and robust TPR
reported at a fixed system FPR.

## Neutral analysis

### The claim attacked

These are claims of ours, in the text as reviewed and still unchanged at 1bb86f2:

- `manuscript/_e_instances.tex:151-153` (§4.4, *Population*): "Whether a file is in the population is a property of
  the file alone, so a detector checks it at inference. A file in the population goes to the monotone detector, and
  any other file to an unconstrained one, which carries no guarantee."
- `manuscript/_f_evaluation.tex:359-363` (§5.4, *What Robustness Costs*, paragraph *Where the guarantee holds*): "A
  monotone detector sends a file outside the population to the unconstrained detector, and that is where the single
  toolkit evasion of each monotone detector happened ... An attacker can build a file outside the population on
  purpose, but such files are rare among benign software, and so stand out."
- `manuscript/_f_evaluation.tex:359-360`: the population "contains \synthetic{89\%} of the malware we attack", in blue
  and without a denominator.

### The premises, checked

1. *Files outside the population go to an unconstrained detector.* **Verified** in the text quoted above.
2. *1.5% of benign test files lie outside the population, above the 1% budget.* **Verified**: in
   `artifacts/experiments/population_clauses/2000/report.json`, 14 of the 938 benign test files below 4 MB lie outside
   (13 incomplete, 1 with an unusual layout), which is 1.49%. The thresholds are set at 1% FPR on the benign test files
   (`_f_evaluation.tex:42-43`). For malware, 80 of 732 (10.9%) lie outside.
3. *One field write takes any file out of the population.* **Verified**, both in the code and in a stored run.
   `catalogue.precondition` rejects a file if any data directory extends past the end, the certificate entry included
   (`src/provexp/featuresets/ember2024/catalogue.py:476-482`). `plain_layout` rejects a SizeOfImage larger than the
   sections need (`catalogue.py:445-447`). Run 137 (`artifacts/experiments/escape_audit/pilot/report.json`) applied
   one write of at most 8 bytes to each of 150 population files. The certificate entry, the debug entry, the reserved
   architecture entry and a raised SizeOfImage each took 150 of 150 files out.
4. *The loader accepts such a file.* **Inferred**, from Microsoft's PE format documentation as recorded in
   `docs/evidence/r7-population-escape.md` §4: certificates "are not loaded into memory as part of the image", and the
   loader maps neither the certificate data nor the debug data. Nothing was executed (settled).
5. *"The paper's own data show such files run"* (C-W1). **False premise.** That a file is in the dataset does not show
   that it executes, a point the meta-review also makes. It does not matter, because premise 4 makes the point on
   other grounds.
6. *The system is never evaluated end to end.* **Verified** for the text as reviewed. Table 5's monotone toolkit
   cells are routed (comments at `_f_evaluation.tex:429-434`).
7. *The 89% is optimistic* (B-W3, A-W4 (2)). **Mostly a preliminary-number artifact.** The 74% and 78.5% counted
   every file, the truncated ones included. Below 4 MB, the 2,000-file set gives 652/732 = 89.1% of malware in the
   population (verified in the same `report.json`), and the pilot's attacked malware give 31/35 (comment at
   `_f_evaluation.tex:364-365`). D's point about the missing denominator is correct. B's request for complete files
   above 4 MB is settled (checklist: "do not propose obtaining the larger files").
8. *B's end-to-end estimate of 10–13%.* **Inferred arithmetic on a design that no longer exists** (see Flaws). Its
   inputs were the 74% share and the routed fallback.

### What the authors have done since the review (decision 11; `docs/evidence/r7-population-escape.md`, `r7-overlay-rule.md`)

The project has already worked through R7 over sessions 48-57. The record:

- **No router (PLAN.md, decision 11).** One monotone detector scores every file. The guarantee is proven on the
  population and measured outside it. The detector's 1% FPR threshold is already set on all benign test files, those
  outside the population included. The system's false-positive rate is therefore the detector's, and the 1.5% problem
  goes away with no extra policy.
- **The escape writes in the threat model.** Run 138, counted end to end from the unescaped originals, showed that
  the hole came from the escape writes themselves, not from the population clauses. The debug-entry write alone
  evaded 3/40 and 4/41 monotone detections, because it raises `debug_size`, a feature the table had marked as one
  that can only fall. So the threat model gained `ent`: the certificate and debug entries may be set to any value, and
  the population lets their data lie past the end of the file (`precondition(..., loose=True)`, the code quoted in
  premise 3). Ten features become two-sided (they can move both ways). The cost, from the header of
  `run/140_widen_entries.sh`, is TPR at 1% FPR 89.6 → 85.7 on the sums and 87.2 → 83.4 on the features. Almost all of
  it comes from signature cloning, which a writable certificate entry permits.
- **Closure under the widened threat model** failed at first through pefile's overlay rule. The extractor now uses
  LIEF's overlay rule. Run 142: closed (0 of 13,326 edits leave), sound, exact.
- **Measured outside the population.** Run 138 step 2 tested an attacker who escapes by raising SizeOfImage. This
  takes the file out of even the widened population, and the attacker then runs a full beam search scored by real
  extraction. The monotone detectors were evaded on 0/40 and 0/41 (`artifacts/logs/escape_pilot.log`, tail;
  verified), and the unconstrained detector on 35/47. MAB-Malware never lowered either monotone detector's score on
  the 12 and 11 detected files outside the population (comment at `_f_evaluation.tex:356`). Run 143 (escape pilot on
  the widened population, `ent` in the attack) is still running: the log shows the certificate step in progress.
- **Still open:** the paper text (PLAN.md step 2b (iv)); the other tables' monotone cells on the `-loose` models
  (step 2b (v), a decision for the user); and at scale, the population share with its denominator, the escape attacks
  ("look actively for further escapes"), and the toolkit attacks on escaped files (step 3).

### Merits

The criticism was right, and the meta-review's sharper form (one write leaves) was right too. Run 137 confirmed it
on every file it tried. As reviewed, the routing handed any attacker the unconstrained detector for the price of four
bytes. The defence offered in the text ("stand out") was contradicted by the paper's own numbers in the same
paragraph. A real reviewer at CCS is very likely to raise it: it is the first thing a security reader checks about a
guarantee with a precondition, and three of four simulated reviewers made it their one change. Had nothing been done,
the meta-review's "fatal" would have been fair.

Some residue survives decision 11 and is real:

- **No proof outside the widened population.** That covers files with a raised SizeOfImage, unusual layouts, and
  structures past the end that the loader does map. The table derived over every file (the "strict table") marks
  2,559 of 2,568 features lowerable (session 46, recorded in `r7-population-escape.md` §2; not re-checked here). So
  in principle, on some file outside the population, nearly any feature can move in the wrong direction. The evidence
  there is measured, not proven: run 138 step 2, MAB-Malware, and run 143 once read.
- **The attacker who builds the file.** An attacker who crafts an incomplete file whose completion by an append lowers
  the score was found once: the certificate case of run 138 step 1. The widening closed that case. Whether a loadable
  file can hide another such structure past the end is **inferred** to be unlikely: the loader reads section data, so
  a section past the end probably does not load (run 137's control row). It has not been searched for systematically.
  The scale-up's "look actively for further escapes" is the place for it.

### Flaws (the authors' advocate)

- **The bypass no longer exists.** The reviewers' objection is to the router, and decision 11 removed it. There is no
  weaker path to step onto. Leaving the population now gives the attacker only the side effects that the table does
  not cover on that file. Two tests of exactly that both found none: the SizeOfImage escape followed by a full
  extraction-scored search (0/40, 0/41), and MAB-Malware on the files outside. The 1.5% objection disappears with it:
  nothing is flagged, and the single threshold already sits at 1% FPR over every benign test file. Decision 11 is
  also simpler than the options the meta-review lists under (b)-(d). It removes a component where they add a rule
  per PE clause. That fits the settled preference for less machinery (memory `constrain-experiment-complexity`), and
  run 137 found several routes, which rules out patching clause by clause.
- **The one-write escape was turned into a finding, not hidden.** The writes are now operations of the threat model,
  and their price is measured: about 4 points of TPR at 1% FPR, nearly all from signature cloning. That is the kind of
  result §5.4 exists to report (memory `findings-not-defense-paper`: the detector's cost is a measurement).
- **"End to end" falls out of the design.** Without a router, Table 5's rows are the deployed system. Unrouted
  denominators (detected out of all attacked malware, outside files included) give exactly the system-level number
  that A-Q3, B-Q1, C-Q1 and D-Q1 ask for. The "evaded by any attack" union in the body is the settled reporting rule
  (decision 12; memory `report-attacks-separately`). It supersedes the meta-review's "never as a union".
- **Two pieces of the criticism rest on numbers that do not hold.** B's 10–13% and the suspicion about the 89% rest on
  counts that include truncated files (premise 7). B's complete files above 4 MB and C's "data show such files run"
  are, respectively, settled and a false premise.
- **What is not claimed.** The paper never claims a guarantee for every file. The settled position is that a detector
  sound over every possible file is "one sentence, not a row" (checklist), and the strict table shows why such a
  detector would detect almost nothing.

## Opinion

**Change the methodology.** The change has already been made (decision 11 in its final form). What remains is to
finish it and put it on the page.

*Would I propose this if no reviewer had raised it?* Yes. The "stand out" sentence contradicts the numbers next to it,
and the one-write escape (found by the meta-reviewer, confirmed by run 137) is a real hole, not a reviewer's misreading.

*Does the criticism restate one of our findings, or attack a claim we do not make?* No. It attacks claims in §4.4 and
§5.4 that we did make. Only side parts do either: B's arithmetic and the 89% doubt (counts on truncated files), C's
premise that dataset files run, and the request for files above 4 MB (settled).

**The smallest change that answers it, beyond what is decided:**

- The text of PLAN.md step 2b (iv), as planned. §4.4: no routing; one detector scores every file, with the proof on
  the population and measurements outside it. §4.3.1: the entry write `ent`. §5.4 *The price*: the `-loose` numbers
  and signature cloning as the place where the cost lies. §5.4 *Where the guarantee holds*: drop "stand out"; give
  the population share as n/N; give the escape result (run 143 now, the scale-up later).
- One sentence there that the reviewers will look for: who chooses the starting file. The attacker edits a detected
  file and may first move it out of the population. That case is measured by the escape attacks, not proven.
- Table 5's denominators unrouted, so the table is the end-to-end evaluation of the deployed system. The scale-up's R7
  items (PLAN.md step 3) already include the population share, the escape attacks at scale and the toolkit attacks on
  escaped files. Within "look actively for further escapes", the one target the evidence points to is a file made
  incomplete so that an append completes a structure. That is the only mechanism that has broken a monotone detector
  so far (run 138 step 1).

**Cost.** Text: about 150-250 words across §4.3.1, §4.4 and §5.4, plus a sentence in Appendix D on the overlay rule
(within the drafting budget). Compute: run 143 (running) and items already in the scale-up. Risk to other results:
§5.4's price rises from 3.9 to about 7.8 points at 1% FPR on the sums (89.6 → 85.7 against 93.5, one seed), and the
other tables' monotone cells must move to the `-loose` models or be marked blue (step 2b (v), the user's call).

**What is lost by not making it.** If the paper kept the router, the meta-review's "fatal" would apply: a four-byte
write would buy any attacker the unconstrained detector, and no in-population evidence would answer B, C or D. Without
the end-to-end count, B and C (the two most confident reviewers) keep their stated reason for weak reject.

**Opinion:** change the methodology (already done in decision 11: no router, and the two entries the loader ignores added to the threat model; what remains is writing it into §4.4 and §5.4 and counting end to end at scale)
