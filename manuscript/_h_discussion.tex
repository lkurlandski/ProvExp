\paragraph{What provenance can place.} Explanation provenance places attribution wherever the extractor reads the
input, and only there. Features that record an absence (e.g., an import-hash bucket that nothing falls into) are
produced by no byte; the pullback hands their attribution to the null element, which keeps the bookkeeping exact and
tells the analyst how much of a decision rests on what the file lacks (about a fifth for the GBDT;
Appendix~\ref{sec:XML:AppLocalizability}). Features computed over the whole file, such as the byte histogram, are
produced by bytes scattered throughout it, so a transfer can name them but not narrow them down to a place; the audit
of Section~\ref{sec:XML:Audit} therefore keeps only candidates whose content can be located. Both are properties of the extractor, visible in $P$ before any explanation is
computed.

\paragraph{Constructing $P$.} Instrumentation records the Shapley provenance exactly for features additive over the
items they read, including hashed counts, and the data flow for entropies and averages. Where the source is not
available, dynamic taint tracking could record provenance automatically, at byte resolution, from an extractor run as a binary. It would make explanation provenance a
drop-in addition to any extractor, and we see it as the natural next step.

\paragraph{Beyond the exact cases.} Section~\ref{sec:XML:Framework} makes the transfers exact for features additive
over their items and a linear model, and the experiments show them working well beyond both. For entropies and
averages, $P$ follows the data flow; their signed Shapley shares could be estimated by sampling coalitions of items, at
extra cost and at the price of the pushforward's normalization. For a tree ensemble, the pullback is G-DeepSHAP's
rescale rule and approximates the interactions between features, which is where the quarter of a planted trigger's
credit that lands on features the trigger does not change comes from (Appendix~\ref{sec:XML:AppTrigger}). The
pushforward comes close to its exact form in one step, and what neither recovers lies mostly in features with
identical provenance, which no transfer can separate; a tool built on the pushforward can report such features as a
single group.

\paragraph{Explainers.} The transfers are linear in the explanation, so they carry it into the other space as it is:
they make a good explanation more useful and leave a weak one as weak as it was. The quality of a transferred
explanation is therefore the quality of its source. We established the method on the GBDT, the standard model for these
features; the same machinery applies unchanged to any other feature-based model, which we return to in future work.

\paragraph{From reliance to attacks.} Our deletion operator keeps every file parseable with its layout intact and is
verified on every file, which makes deletion a clean measurement of reliance, but it does not keep programs running.
Section~\ref{sec:XML:Applications} therefore rests its security conclusions on changes that the Windows loader
ignores or allows, following the format's documentation, so the changes are ones an attacker could make; we did not
execute the modified files. Section~\ref{sec:XML:Comparison} uses two such changes, a gradient attack confined to
loader-ignored bytes and edits of loader-safe fields, to ask whether the pullback predicts a transfer to the
feature-based detector. Our attacker stays deliberately narrow:
appending content, injecting sections, or packing evade MalConv more easily~\cite{demetrio2021adversarial}. An
explanation of the original file measures the evidence that a change can remove, not the evidence that new content
adds, which is why the gradient attack's rise in the GBDT's score is explained but not predicted; extending the
transfer analysis to attacks that add content is a natural next step.

\paragraph{Mitigation.} The audit points to a countermeasure, and Section~\ref{sec:XML:Audit} shows that it is a
trade-off: zeroing the fields an attacker can change removes most of the measured attack surface but costs a few points
of clean detection, because the same fields also carry legitimate signal. Retraining with the fields removed may
recover that signal~\cite{lucas2023adversarial}, and an attacker may look for other fields once these are gone; both belong to an ongoing audit
rather than a one-time fix, and the pushforward makes repeating the audit cheap. The disagreement triage points the
other way, to feature engineering: when the raw-byte detector alone flags a file, three quarters of its evidence lies
in content the feature-based detector's features do not read, which is where a new feature would help.

\paragraph{Beyond Windows executables.} Nothing in the method is specific to PE files. $P$ depends only on which
input elements produce which features, so the transfers apply to any classifier whose features a program computes from
a structured input: detectors over Android apps (permissions, API calls, and strings extracted from the manifest and
the bytecode), documents, or network traffic (flow statistics computed from packets), where the elements would be
bytes, instructions, or packets. Each needs its extractor instrumented once. We have
evaluated only PE files and EMBER features, whose extractor mixes the kinds of features a program computes (fields
read directly, counts, hashes, and aggregates over the whole file); other extractors may lean toward one kind or
another, which changes how sharply their explanations can be placed in the input. \synthetic{To test this beyond
Windows, we instrument a Drebin-style Android extractor (manifest permissions, intents, API calls, and strings) and
